# Contributing to Kirikae

Thanks for helping! Issues and pull requests are welcome in English or Portuguese.

## Before you start

- Read [LEGAL.md](LEGAL.md). In short: clean-room work only, no GPL code, no leaked or NDA material,
  and no game data of any kind (binaries, shaders, textures, screenshots, dumps, keys, firmware).
- Kirikae only reads decrypted dumps. Changes that add decryption are not accepted.
- Game-specific fixes belong in a plugin (`kirikae build --plugin`), not in the runtime, unless they
  fix how the hardware or the system really behaves.

Start with [ARCHITECTURE.md](ARCHITECTURE.md) for a map of the code.

## Building and testing

```bash
cargo build --release
cargo test --release
cargo clippy --release --workspace --all-targets -- -D warnings
```

On Windows, set `CARGO_TARGET_DIR` to a short folder if the project lives in a long path. CI runs the
same three commands on Windows and Linux.

`docs/progress` is generated by `python tools/progress.py`. Leave it out of pull requests: it changes
with every runtime change, so it would conflict between them. It is regenerated after merging.

## Organizing the code

- One concept per file, named after what it models (`vic.rs`, `arbiter.rs`, `hid.rs`).
- Keep files under about 1000 lines. When one grows past that, turn it into a folder with a `mod.rs`
  and split it by concern; a big `impl` can be spread over several files of the same module.
- Modules that are folders use `mod.rs`, as `gpu/`, `host1x/` and `nvn/` do.
- New services go in `crates/rt/src/services/`, one file per service family.

## Pull requests

- Keep each pull request focused on one change.
- Commit messages start with `feat:`, `fix:` or `chore:`, in English, short and to the point.
- Match the surrounding code; the code base keeps comments to the required ones (`// SAFETY:` on
  `unsafe` blocks and third-party license notices).
- Describe how you tested it: the test that covers it, or what you ran and what you saw.
